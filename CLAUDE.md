# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The website for Gytte Lane Golf Society (Syresham, Northamptonshire, founded 1994). It is **not a build project** — there is no package.json, bundler, or test suite. It's a handful of self-contained static files deployed as-is:

- `index.html` — the entire site (~7,600 lines: all pages, styles, and JS in one file)
- `login.html` — the only sign-in surface (see Auth below); `index.html` has no login UI of its own, it links out to this page
- `sw.js` — service worker for offline support
- `docs/architecture.html` — hand-built SVG component/infrastructure diagram, kept up to date as services are added (e.g. Stripe, Resend) — see "Third-party services" below for the current list
- `supabase/functions/` — the project's only server-side code: two Deno Edge Functions (`create-checkout-session`, `stripe-webhook`) for Stripe, deployed via the Supabase Management API (no CLI/Docker on the dev machine — see Payments below)
- `CHANGELOG.md` — **frozen as of Phase 12 (2026-07-12) and explicitly not maintained further** (says so at the top of the file itself). Useful for *why* early decisions were made, but everything since is CLAUDE.md-only — if you change something, document it here, not there.

No npm, no build step, no local dev server config. To preview changes, open `index.html` directly in a browser or serve the directory with any static file server. **Deployment is automatic**: Netlify is connected directly to this GitHub repo (`GyttesGolf/GytteLaneGolf`) and deploys on every push to `main` (verified via the Netlify API, 2026-08-04) — pushing to `main` is a live production deploy, there's no separate staging/review step unless you add branch protection or a PR requirement yourself.

## Working in this codebase

- Everything lives in `index.html`: HTML sections, a single `<style>` block, and a single `<script>` block at the end. There's no module system — all JS is global functions and top-level `let`/`const` state (`events`, `committee`, `players`, `signups`, `allScorecards`, `isLoggedIn`, etc. — see top of the main script block).
- Find your way around by searching for the `/* ===== name ===== */` comment banners — the script is organized into clearly delimited regions (helpers, navigation, render: events, edit: events, render: committee, committee login, render: gallery, render: news, render: players, render: home, events map, live scores, offline score queue, render: rules, render: hall of fame, courses & ratings, payments, accounts, bottom nav, groupings, leaderboard, lightbox, init). The HTML above it has matching `<!-- ===== NAME ===== -->` banners for each page section.
- Rendering is manual DOM string-building: each `render*()` function rebuilds an element's `innerHTML` from the in-memory state arrays. There's no virtual DOM/diffing and no reactive framework — after mutating state (or after a Supabase write), call the relevant `render*()` function yourself.
- Navigation between "pages" (Home, Events, Committee, Players, Gallery, News, Shop, Live Scores, Rules, Hall of Fame, Admin, Groupings, Leaderboard) is done client-side via `goTo(sectionName)`, which shows/hides `<section>` elements — there's no router or URL-based state. The "Admin" nav item/section is still `data-section="accounts"` / `sec-accounts` / `renderAccounts()` internally (renamed in the UI only, 2026-08-04, to avoid a larger rename) — it's an admin-only hub with its own sub-tabs (`adminSubView`: "Accounts" for financials, "Admins" for who has `is_committee`), following the same sub-tab pattern Live Scores uses (`setLiveSubView`/`liveSubView`). More admin tooling is expected to land here as more sub-tabs, not new top-level nav items.
- CSS custom properties at the top of `<style>` define the design system (colors, fonts) — check that block before hardcoding colors. Current palette is burgundy/ink (`--ink:#4B1320`) with brass/gold accents (`--brass:#B8862F`); the diagonal club-tie stripe (ink/claret/brass) is the repeated visual signature across header, dividers, and nav.
- Mobile-first: a bottom tab bar (`BOTTOM NAV`) plus a "More" drawer handle primary navigation; layout throughout should be checked at phone width first.

## Backend (Supabase)

All content, auth, and file storage is Supabase (PostgreSQL + Auth + Storage + Realtime, free tier). Client init and config are near the top of the script block (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `const db = window.supabase.createClient(...)`). There is no server-side code in this repo — all reads/writes happen client-side via `db.from('<table>')...`.

## Deleting a society and all its data

Not exposed in the UI (deliberately — see the "should we add a delete button" discussion this was decided in; the plan was strong confirm-by-typing-the-name friction at minimum, never a bare button, and even that hasn't been built). To actually remove a society, run SQL directly against Supabase (via the Management API's `/database/query` endpoint, same as everything else in this file) deleting from every table that carries `society_id`, in this order (children before the `societies` row itself; verify this list is still current with `select table_name from information_schema.columns where column_name='society_id'` before trusting it, in case a table gains/loses the column later):

```sql
delete from activity_log where society_id = '<id>';
delete from hole_scores where society_id = '<id>';
delete from scorecards where society_id = '<id>';
delete from group_players where society_id = '<id>';
delete from groups where society_id = '<id>';
delete from refunds where society_id = '<id>';
delete from event_payments where society_id = '<id>';
delete from expenditures where society_id = '<id>';
delete from signups where society_id = '<id>';
delete from course_ratings where society_id = '<id>';
delete from courses where society_id = '<id>';
delete from honours where society_id = '<id>';
delete from rules where society_id = '<id>';
delete from news where society_id = '<id>';
delete from gallery where society_id = '<id>';
delete from committee where society_id = '<id>';
delete from players where society_id = '<id>';
delete from events where society_id = '<id>';
delete from societies where id = '<id>';
```

`platform_admins` has no `society_id` (deliberately independent, per Phase 3) — nothing to clean up there. If the society had a `logo_url` or any `gallery`/`committee` photos uploaded to the `photos` Storage bucket, those file objects aren't touched by the SQL above and would need deleting separately via `db.storage.from('photos').remove([...])` or the Supabase dashboard's Storage browser, or they'll just sit there as orphaned files (harmless but wastes the free-tier storage cap). Always `select count(*)` per table for that `society_id` *before* deleting, and confirm with the user first — this is fully destructive with no undo, per the same reasoning that kept it out of the UI.

**Sharp edge found building the above, worth remembering**: requesting the inserted row back from a public insert (`.select()` chained in supabase-js, or `Prefer: return=representation` over raw REST) fails with an RLS error *even when the insert's own `WITH CHECK` passes*, if the row isn't visible under that table's `SELECT` policy for the calling role. PostgREST's implicit `RETURNING` is itself subject to `SELECT` RLS. `logActivity()` deliberately never chains `.select()` for this reason — anonymous/public inserts elsewhere in this codebase (`signups`, `course_ratings`) already avoid this by the same omission, but if you're adding a new public-insert call, don't chain `.select()` unless that table's `SELECT` policy actually allows the inserting role to read it back.

**Product direction: this is meant to become a multi-tenant "Golf App" platform**, not just Gytte Lane's own site — the eventual goal is multiple golf societies running on this same codebase/database, with a "Golf App Platform Admin" role able to see activity across all of them (distinct from a single society's own `is_committee` admins, who should stay scoped to their own society once multi-tenancy is real). **Guiding principle for this direction: prefer the latest technology that offers the best value and stays manageable with Claude** — i.e. don't default to legacy/heavyweight enterprise tooling or infrastructure that needs its own ops burden; prefer modern, low-maintenance, high-leverage services (managed/cloud-hosted over self-hosted, API-accessible over dashboard-only) that fit this project's zero-build, zero-backend ethos and that Claude can actually help operate directly (e.g. via API access), not just advise on from the sidelines. This is why, for the analytics work being planned as of 2026-08-05, Grafana Cloud (managed, free tier, native Postgres data source) is favoured over self-hosting Grafana.

**RLS is scoped and enforced as of 2026-08-04, and society-scoped as of 2026-08-05** (tightened from an earlier state where every write was open to `public` with no auth check at all — verify this hasn't regressed by re-running `select tablename, policyname, cmd, roles from pg_policies where schemaname='public'` before assuming it's still true). Current model, backed by a `public.is_admin(target_society_id uuid default null)` SQL function (checks `auth.email()` against `players.is_committee`/`active`, and against `players.society_id = target_society_id` when an argument is passed — every per-table policy passes that row's own `society_id`):
- **Public** (no login) SELECT on all content tables except `expenditures` (admin-only, since it's never shown to non-admins anyway); public INSERT on `signups`, `course_ratings`, and (as of 2026-09-05, see bug note below) `scorecards`/`hole_scores`; public UPDATE on `course_ratings` and `hole_scores` (event sign-up, course rating, and live score entry are all deliberately login-free, self-service by picking your own name/group from a dropdown — there's no identity check tying a row to the person who actually created it).
- **Member** (any authenticated player, `is_committee` or not) INSERT on `gallery` only — matched client-side by a separate `isMember` flag (any active signed-in player, computed in `initAuth()` alongside `isLoggedIn`), which gates the gallery upload form in `renderGallery()`. `isLoggedIn` still means admin specifically; edit/delete on existing gallery items stays admin-only.
- **Admin** (`is_committee`) — everything else: all UPDATE/DELETE, and INSERT on every table other than `signups`/`course_ratings`/`scorecards`/`hole_scores`/`gallery`.
- This is enforced at the database level now, not just hidden in the UI — confirmed by a live anonymous `curl` against the REST API returning 401 on a write attempt.

**Bug fixed 2026-09-05: live scoring was silently write-only for the group that entered it.** The society reported that during a live round, each group could see their own scores on the leaderboard but not other groups'. Root cause: `scorecards` and `hole_scores` INSERT (and `hole_scores` UPDATE, needed for the `upsert` in `processScoreQueue()`) were left admin-only (`is_committee`) from the 2026-08-04 RLS tightening pass, but score entry (`/* offline score queue */` region) has always been designed as no-login, self-service by any group marker — same as `signups`/`course_ratings`. A non-admin marker's score taps got queued locally and displayed via `mergeQueueIntoHoleScores()`'s client-side overlay (making it *look* like it worked on that device) but the actual Supabase write was rejected by RLS and never reached the database, so no other device ever saw it. Confirmed live: `scorecards` had rows from the test session, `hole_scores` had none. Fixed by adding `Public insert scorecards`, `Public insert hole_scores`, and `Public update hole_scores` policies (same shape as the existing `course_ratings` public insert/update pair) — admin INSERT/UPDATE/DELETE policies stay in place alongside these (RLS policies OR together, so this only adds permission).

## Auth: Supabase Auth (password + passkey + magic link), admin gated by `is_committee`

The Hanko/Supabase migration referenced in older commits is finished — `index.html` no longer loads `@teamhanko/hanko-elements` or has any login modal of its own. `login.html` is the sole sign-in surface. As of 2026-08-18 it offers three ways in, all funnelling through `completeLogin()`, which looks the signed-in email up in `players` and requires `active !== false`:

- **Email + password** (`signInWithPassword()`) — the primary, default form on the "Member?" panel now (passkey is offered as a secondary button below it). Wrong password and "no password ever set" both surface as the same generic Supabase error by design (can't be used to enumerate accounts), so the UI just points at "Forgot password?" either way rather than trying to distinguish them.
- **Passkey** (`signInWithPasskey()`/`registerPasskey()`, WebAuthn via Supabase's `experimental.passkey` flag) — still supported, now secondary to password.
- **Magic link** (`handleEmailSubmit()`) — only reachable via the "First time?" panel now (the old "Member?" panel's separate magic-link fallback was removed; forgotten/never-set passwords go through password reset instead, see below).

**Known sharp edge (passkey)**: `signInWithPasskey()`'s own response doesn't reliably carry the user's email (it's an experimental Supabase feature) — always re-fetch via `sb.auth.getUser()` before trusting `user.email`, rather than the direct sign-in response. Getting this wrong produces a false "this email isn't registered" error for genuinely registered players.

**First-time flow / onboarding model is deliberately invite-only, not self-registering**: a captain/admin must add someone to `players` (with their email) before they can sign in at all — `completeLogin()` rejects any email with no matching active `players` row ("This email isn't registered. Contact your captain."). A first-time member's magic link carries a `?setup=1` redirect param; landing back with a valid session *and* that param shows a **"Secure your account"** screen (`panel-setup` in `login.html`) offering to set a password and/or register a passkey before continuing in — this validates the player via `completeLogin(user, {noRedirect:true})` first (closing a real gap where the old flow auto-triggered passkey registration for *any* email that could request a magic link, registered or not, before ever checking the `players` table).

**OTP code fallback**: the "First time?" panel also reveals a plain numeric code field (`verifyEmailCode()`, `sb.auth.verifyOtp({email, token, type:'email'})`) after a magic link is sent — Supabase generates this code alongside every magic link regardless. This exists because magic links are vulnerable to being silently consumed before the real click: email security scanners/"Safe Links"-style prefetchers visiting a link to check it's safe burn its one-time token, and the failure mode is silent — no error, just landing back on the plain login screen. Confirmed directly by reproducing it (reusing an already-visited token gives the exact same symptom). The code has no link for anything to prefetch, so it's immune.

**Password reset** (`handleForgotPassword()` → `sb.auth.resetPasswordForEmail()`) is a genuinely different Supabase mechanism from the plain magic link — it sends Supabase's separate "Reset Password" email template, and its link, on return, fires a `PASSWORD_RECOVERY` auth event rather than just signing someone in. `login.html` listens for that event and shows a "choose a new password" panel (`panel-recovery`) instead of redirecting straight into the site. Works the same whether someone forgot an existing password or never set one — Supabase doesn't distinguish those cases.

**Auth-state handling is event-driven, not load-driven**: everything above is wired through a single `sb.auth.onAuthStateChange()` listener rather than a one-shot `getSession()` check inside a `window.addEventListener('load', ...)` — a session arriving from a magic-link/reset URL is established asynchronously by Supabase's own internal processing, which isn't guaranteed to finish before `load` fires, so polling at a fixed point is a real race (found and fixed live: the fix param (`?setup=1`) also has to be captured *once* at parse time rather than re-read from `window.location.search` inside the listener, since the first handler firing strips it and a second firing for the same sign-in — `INITIAL_SESSION` then `SIGNED_IN` both fire — would otherwise see it already gone).

Auth is **not** a single shared committee account — any active player can sign in via `login.html`. But signing in alone doesn't grant admin rights: `index.html`'s `initAuth()` only sets `isLoggedIn` (admin — gates all edit/delete/add UI and the Admin/Accounts page) when the signed-in email matches an active player whose `is_committee` column is also `true`. A separate `isMember` flag (any active signed-in player, admin or not) now has real UI of its own — see "My Account" below; this closed a real gap where a signed-in non-admin previously had *no visible indication they were logged in at all*.

The player-edit "Admin access" checkbox (DB column `is_committee`, element id `ep-committee-${p.id}` — name kept for now to avoid a schema rename) is what actually grants edit rights. This is unrelated to the "Committee" nav page/table (`committee` table, `renderCommittee()`) — that's the public list of club officers (captain, secretary, etc.), a different concept from site admin permissions. All user-facing text uses "Admin"/"Admin access" for the permission concept and "Committee" only for the officers page.

### My Account (2026-08-18)

A real self-service area for any signed-in member (`sec-myaccount` / `renderMyAccount()`), reached via the nav's account button — that button (`#nav-lock-btn`, top-right / More drawer) is now driven by `isMember`, not `isLoggedIn`: "Sign in" when signed out, "My Account" when signed in (icon changed from a padlock to a person, and the `.nav-lock-btn svg` CSS rule that force-filled it solid was updated to match the outline style used everywhere else in the nav). Three sub-tabs, same `adminSubView`-style pattern as the Admin hub (`myAccountSubView`: 'profile' | 'signups' | 'history'):

### Email delivery: Resend (2026-08-18)

Supabase's default/shared mailer caps out at **2 emails/hour project-wide** — fine for occasional testing, not for real multi-member usage (confirmed live: hit this exact limit mid-testing). Custom SMTP now points at [Resend](https://resend.com) (`smtp.resend.com:465`, free tier). Sender is `noreply@gyttelanegolf.co.uk` — **the verified apex domain, not a `send.` subdomain**: DNS records were added under a `send.gyttelanegolf.co.uk` prefix (Netlify DNS — this domain's nameservers point at NS1/Netlify's DNS product, not GoDaddy directly, despite GoDaddy holding the registration; `dns_zone_id` on the Netlify site object confirms it isn't Netlify-DNS-zone-linked via API either, so this had to be edited by hand in the Netlify dashboard, not scripted), but Resend only verifies MX/SPF domain ownership through the DKIM+DMARC records — which live at the apex (`resend._domainkey.`/`_dmarc.`) — so the "Domain" entity Resend actually verified is `gyttelanegolf.co.uk` itself; sending from the `send.` subdomain specifically failed with "domain not verified" until the sender was switched to the apex.

**Sharp edge, cost real time**: Supabase's auth config API (`PATCH .../config/auth`) does **not** do field-level merge on the `smtp_*` block — sending only the one field you want to change (e.g. just `smtp_admin_email`) silently wipes every other `smtp_*` field back to `null`, falling back to the rate-limited default mailer with no error. Always send the *entire* SMTP config (`smtp_host`, `smtp_port`, `smtp_user`, `smtp_pass`, `smtp_sender_name`, `smtp_admin_email`, `smtp_max_frequency`) together in one PATCH, every time, including when only changing one field. Separately, `rate_limit_email_sent` is **not** automatically raised just by configuring custom SMTP (it silently reset to `2` at one point despite SMTP being otherwise correctly configured) — set it explicitly (currently `100`) in that same combined payload.

New Resend API keys only show their value once at creation and can't be retrieved again — if lost, create a new one rather than trying to recover the old one (no need to delete the old key first).

## Payments

Two ways to pay for an event, side by side — **never mandatory to use either specific one**, by explicit design decision:

- **Manual bank transfer** — an admin-entered `society_payment_details` table (`payment_account_name`/`sort_code`/`account_number`/`reference_note`, one row per society), shown on an event's detail page only to signed-in members (`isMember`). This is a separate table from `societies` on purpose: `societies` has an unrestricted public `SELECT` policy (needed for branding), so bank details were briefly added there and then immediately moved out once that was noticed — putting sort code/account number on a publicly-readable table would have made them world-readable via a direct anonymous REST call regardless of any client-side login check. Gated by a new `is_member(target_society_id uuid default null)` SQL function (same shape as `is_admin()`, minus the `is_committee` requirement). Deliberately **not** included in the offline `localStorage` snapshot (`saveDataSnapshot`) — caching real bank details unencrypted on-device would undermine the point of the RLS fix.
- **Stripe Checkout** (`payWithStripe()` → `create-checkout-session` Edge Function → real Stripe-hosted checkout page → `stripe-webhook` Edge Function marks `event_payments.paid = true` on `checkout.session.completed`) — a standard (non-Connect) single Stripe account, Gytte Lane only for now. The price is always looked up server-side from the event's own `cost` field (or an existing custom per-player amount), the client only ever supplies `event_id`+`player_id` — never trust a client-supplied amount. `stripe-webhook` is deployed with `verify_jwt: false` (Stripe calls it directly with no Supabase auth at all; the real authentication is the Stripe signature check inside the function) while `create-checkout-session` keeps the default `verify_jwt: true`. `event_payments` gained `payment_method` (now `'in_app'`/`'other'` — see below) and `stripe_session_id` columns; the webhook's upsert relies on the pre-existing `unique(event_id, player_id)` constraint. Both Edge Function secrets (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`) are set via the Supabase Management API, never committed or echoed in chat.
- **Removing a signup** (`removeSignup()`): an *unpaid* player's `event_payments` row is deleted (otherwise it's orphaned and keeps counting as "outstanding" — the root cause of a wrong outstanding figure once). A *paid* player's row is **kept** with `cancelled_at` set, so the money and its refund stay on record (2026-09-23).
- **Card payments are per-society, platform-admin controlled** (2026-09-23): `societies.stripe_enabled` (Platform → Edit society → "Card payments (Stripe) enabled"). There's one Stripe account behind everything, so it's only on for Gytte Lane. `create-checkout-session` refuses any other society (403) and any player from a different society; `cardPaymentsEnabled()` hides "Pay now" client-side. A `before update` trigger (`protect_society_stripe_flag()`) reverts changes to the flag unless the caller is a platform admin (or `postgres`/service role) — society admins can otherwise update their own `societies` row for branding. The function only redirects back to the society's own `custom_domain` (or `www.` form), never an arbitrary client-supplied origin.
- **Cancellations & refunds** (2026-09-23): `event_payments` gained `cancelled_at`, `refunded_amount`, `refunded_date`, `stripe_payment_intent`; new append-only `refunds` table (one row per refund, `method` `'in_app'`/`'other'`, `stripe_refund_id` unique; RLS: admins of that society, or the player themselves by email, can read; admins insert/delete). In-app refunds are made **in the Stripe dashboard** — the webhook's `charge.refunded` handler looks the payment up by `stripe_payment_intent`, lists the charge's refunds from Stripe, upserts them into `refunds`, and sets `refunded_amount`. Refunds of 'other' payments are recorded by an admin via "Record refund" on the event's **Cancelled** list (`recordManualRefund()`). `isPaidRecord()` means paid *and not fully refunded*; `netCollected()` (paid − refunded) is what Accounts counts as income; `isCancelledPayment()` = `cancelled_at` set *and* not signed up again. A player who re-joins after a full refund pays afresh (the webhook / `togglePayment()` reset the row; `refunds` keeps the history). Shown in: the event's "Cancelled" list (status for everyone, amounts + actions for admins), My Account → Payments & Sign-ups → "Cancellations & refunds", and Accounts ("£X refunded").
- **Payment method terms** (2026-09-23): `event_payments.payment_method` / `refunds.method` are `'in_app'` (paid through the app's payment system — Stripe today, but the term is deliberately provider-neutral) or `'other'` (bank transfer, cash, anything else; the default). Chosen with the user: "Online" was rejected (confused with internet banking), and "Direct" too. **Only in-app gets a visible tag** (`IN_APP_TAG`, `.inapp-tag` — on the admin payment list, the Cancelled list, and My Account; deliberately NOT on the public Who's playing list, tried and removed at the user's request) — 'other' is the unremarkable default and is never labelled in the UI. In-app payments' tick box and amount are locked on the admin payment list (Stripe is the record; refunds go through Stripe). Check constraints enforce the two values.
- **In-app payment fees** (2026-09-23): the webhook stores Stripe's *actual* fee (`event_payments.stripe_fee`, from the charge's balance transaction — not a configured rate, which would drift with card type and price changes). Accounts shows income gross, with a per-event "£X in-app (fees £Y)" note, and the fees as an "in-app payment fees" expenditure category (`inAppFeeExpenses()`, computed, never stored in `expenditures`, excluded from the editable expenditure log) — on screen and in the PDF. Stripe keeps its fee on refunds, so refunded in-app payments' fees still count. Known gap: if an in-app payment is fully refunded and the player then pays again, the row is reset and the first payment's fee is overwritten.
- **Webhook behaviour**: marks paid only when `payment_status === 'paid'`; anything that isn't ours (unknown event types, no matching metadata/payment) gets a 200 and is ignored so Stripe doesn't retry it. The Stripe webhook endpoint must be subscribed to `checkout.session.completed`, `charge.refunded` and `charge.updated` — Stripe often attaches the fee (balance transaction) a few seconds after checkout completes, so `stripe_fee` is usually null at payment time and filled in by `fillMissingFee()` on the later `charge.updated` (or `charge.refunded`) event.

Neither payment table nor the Stripe functions require the site to be "gated" (login-walled) first — Stripe handles its own PCI compliance for card data, and the bank-detail gating above was specifically about not leaking real account numbers, which doesn't apply to a Checkout redirect.

## Accounts (Admin hub)

## A recurring bug class worth knowing about: missing `society_id` on inserts

Found and fixed **nine separate call sites** across two sweeps (the first regex only matched inline object-literal inserts `db.from(x).insert({...})`, missing `insert(payload)` variable-based calls — the second sweep used `db\.from\('\w+'\)\.insert\(` and checked every match by hand): `honours` (×2), `course_ratings` (×2), `committee`, `gallery`, `news`, `rules`, `expenditures`, plus later `groups` (the Live Scores → Groupings tab's own "+ Add group" button used a *different* insert path, `addGroupFromScores()`, than the standalone Groupings page's `addGroup()`, and only the latter got fixed in the first pass). Every one of these is a leftover gap from the original multi-tenancy migration — a `NOT NULL society_id` column with an insert that just never got updated to stamp it. **If you add a new `db.from(...).insert(...)` call anywhere in this file, double-check `society_id` is in the payload** — there's no lint or framework catching this, and the failure mode is a silent "save failed" with no other clue.

## Offline support (`sw.js` + in-page logic)

- `sw.js` precaches the app shell and CDN libraries; navigation requests are network-first (falls back to cache offline), other assets are cache-first. It explicitly never intercepts `*.supabase.co`, `api.postcodes.io`, or `*.tile.openstreetmap.org` — live data must always hit the network.
- Separately, `index.html` keeps its own `localStorage` snapshot of all loaded data (`saveDataSnapshot`/`restoreDataSnapshot`, key `glgs-data-cache`) so the page has content to render even before/without the service worker.
- Live scoring has its own offline write queue (`/* offline score queue */` region): score taps are saved to `localStorage` first and synced to Supabase opportunistically (plus a periodic retry), so scoring works with no signal at the course and catches up later.
- **Setting up a new scoring group is also fully offline now** (was not, originally — `startScoring()` used to require a live connection to create each player's `scorecards` row before scoring could begin *at all*, which defeated the point of the queue above for the one moment signal is most likely to be weak, right at the start of a round). Each player now gets a temp local id (`local-<eventId>-<playerId>-<timestamp>`) immediately, and a second queue (`scorecardQueue`, mirroring `scoreQueue`) syncs the real `scorecards` rows in the background, remapping every `holeScores`/`scoreQueue` entry from the temp id to the real one the moment it lands (`processScorecardQueue()`). A `23505` conflict (another device already created the same scorecard) is treated as success by adopting the existing row rather than erroring. Any place a scorecard id gets embedded into an `onclick` attribute must use `JSON.stringify(sc.id)` (not the bare value) — a real bug shipped once from forgetting this, since a temp id is a string and needs quoting in the generated HTML while a real DB id is a number and must not be.

## Live scoring specifics

Stableford scoring by hole, entered per group. The blackout hole (scores freeze for non-committee viewers to preserve the finish as a surprise; admin logins bypass it and see full live standings) is computed as `holes - 5` via `blackoutHoleFor()` rather than a fixed constant, so it scales for 9-hole rounds too (see "Multi-round events" below) — there is no more standalone `SCORE_BLACKOUT_HOLE` constant. "Finalise" (`finaliseScores()`) writes only the winner into `honours` via `syncHonourForEvent()`, keyed by event id (and round id, see below) so re-finalising updates rather than duplicates — there's no separate table recording the full top-3/score summary despite what the button copy implies.

### login.html's visible branding was never actually per-society (2026-09-06)

`resolveSociety()`/`updateHomeScreenIcon()` (added earlier) only ever branded the browser-tab favicon/manifest/theme-color — the page itself (crest image, "Gytte Lane Golf Society" name, "Syresham · Est. 1994" location line, and the burgundy background gradient) was **hardcoded static HTML/CSS**, so every society's sign-in page looked identical regardless of whose domain it was loaded from. Found live setting up Lem's Golf Society as a real second society. Fixed by `applyLoginPageBranding(soc)`: sets `document.title`, the `#login-crest` image src (`soc.logo_url || placeholderCrestDataUri(soc)`, same fallback pattern as the icon), `#login-society-name`/`#login-society-loc` text, and derives the page's background gradient from `soc.primary_colour` via a small local `darkenHex()` helper (doesn't need to match `index.html`'s real HSL-based `adjustLightness()` — this is decorative only). Applied unconditionally whenever a society resolves (including for Gytte Lane itself) rather than special-cased, since Gytte Lane's own row already has its real values backfilled — same reasoning as every other per-society fallback in this file.

**Also fixed same day**: every remaining gold accent in `login.html` (pill borders/backgrounds, the sign-in button gradient, focus-state borders, the loading status message, the "Contact your committee" link, and the envelope/hand pill icons) was still hardcoded brass/burgundy hex. Rather than precomputing rgba strings per alpha value in JS, these now read from five CSS custom properties (`--acc`, `--acc-light`, `--acc-dark`, `--ink-1`, `--ink-2`, defaulted to Gytte Lane's own values in `:root`) combined with `color-mix(in srgb, var(--acc) N%, transparent)` for the alpha-blended tints — `applyLoginPageBranding()` just sets those five properties once via `lightenHex()`/`darkenHex()` and the whole page's cascade updates. `color-mix()` needs a reasonably modern browser (iOS Safari 16.2+/2022); older ones just keep the accent solid without the tinted variants, a graceful-enough degradation.

### Player uniqueness is per-society, not platform-wide (2026-09-06)

`players.email` and `(first_name, last_name)` were both originally unique **across the whole table**, not scoped by `society_id` — a leftover from before real multi-tenancy existed. That blocked a completely realistic scenario: the same person belonging to two different societies on the platform (found while setting up a personal test society for Laurence himself, alongside his existing Gytte Lane player row, using the same email). Replaced with `players_society_email_key unique(society_id, email)` and `players_society_name_key unique(society_id, first_name, last_name)`.

**This required a matching fix in `login.html`**, not just the schema change: `completeLogin()` used to look a signed-in email up in `players` with no `society_id` filter at all, trusting the (then-true) assumption that email was globally unique. Once that's no longer guaranteed, a bare email lookup on Club A's login page could silently return Club B's row instead (whichever one Postgres happened to return first) for someone who belongs to both. Fixed by adding `resolveSociety()` (the same custom-domain → subdomain → oldest-society-fallback resolution `index.html`'s `loadData()` already does, extracted to a shared memoised helper since `login.html`'s icon-setup code needed the same resolution too) and filtering the players query by `.eq('society_id', soc.id)`. `index.html` itself needed no equivalent fix — every player lookup there already operates on the in-memory `players` array, which `loadData()` only ever populates pre-scoped to the current society.

### Focus mode (2026-09-06)

An immersive, chrome-free screen for entering scores and checking the leaderboard, entered by tapping **Start / Resume** on a group (`startScoring()` sets `scoringFocusMode = true`) and left via a ✕ button (`exitScoringFocus()`). Backed by one flag (`scoringFocusMode`) plus a `body.scoring-focus` CSS class that hides the header, desktop nav, bottom nav, and the Live Scores page's own eyebrow/title, letting `#live-scores-content` take over the full viewport (`position:fixed; inset:0`) with its own dark (ink-background) layout. `syncScoringFocusClass()` is the single source of truth for whether that class is actually applied — it also requires `#sec-scores` to be the currently active section, so a realtime update firing while the user has navigated elsewhere can't hijack an unrelated page; `goTo()` explicitly clears `scoringFocusMode` when leaving Live Scores for the same reason.

- **Two screens, one shell**: `renderScoringFocus()` dispatches to `renderFocusEntry()` or `renderFocusLeaderboard()` based on the existing `liveSubView` state — a "🏆 Leaderboard" / "⛳ Scoring" pill button in the top corner (next to ✕) toggles between them via the existing `setLiveSubView()`, without ever leaving focus mode. Both reuse all the same underlying data/logic as the normal chrome views (`getLeaderboard()`, `scorecardFor()`, `blackoutHoleFor()`, etc.) — only the markup differs.
- **No login in live scoring, so no real "my row"**: scoring is deliberately open/no-login (see RLS section above), so there's no authenticated identity to highlight "my" leaderboard row against. `scoringPlayerIds` (the group currently being scored on *this device*) is used as a stand-in — those rows get a highlighted `.lb-row.me` style instead.
- **Admin finalising stays in focus mode**: admins already bypass the blackout in the normal chrome view, so `renderFocusLeaderboard()`'s admin branch shows the full, unfrozen standings plus a "✓ Every player's finished" banner and the real Finalise button once every started player is done — no need to exit focus mode just to wrap up. For a multi-round event, this points the admin to exit and use the "🏆 Overall (combined)" tab instead, since **focus mode has no round-switcher of its own** — Start/Resume always begins on one concrete round, and reaching Overall (or a different round) requires exiting first. `renderFocusLeaderboard()`'s `liveRoundId === null` branch (Overall inside focus mode) is a defensive fallback for this reason — not normally reachable.
- **A real reveal, not just "sealed" forever**: previously (both before and after this feature) a non-admin who finished scoring just saw a static "Scores are sealed!" placeholder that never changed once the admin actually finalised. Focus mode's non-admin leaderboard branch now checks for a matching `honours` row (same `event_id`/`round_id` lookup `syncHonourForEvent()` itself uses) and swaps in an actual winner reveal (name + `winner_score`, if the honours row has one) the moment it exists. The normal (non-focus) chrome view still only shows the static "sealed" message — only focus mode got the reveal treatment so far.
- Mocked up first as a standalone HTML artifact before building (five iterations covering entry, leaderboard, the frozen state, admin's finalise screen, and the reveal) — worth doing again for any UI-shaped feature like this one, since several rounds of "what would X see here" came up before writing any real code.

### Multi-round events (2026-09-05)

An event can optionally have several **rounds** — e.g. a weekend/tour with a Saturday and Sunday round, each scored separately, potentially at different courses — while still being ONE event with ONE signup list and ONE payment (rounds don't touch `signups`/`event_payments` at all). Backed by a new `rounds` table (`event_id`, `label`, `date`, `course`/`course_id`, `tee_time`, `holes` — 9 or 18, default 18, `sort_order`) plus a nullable `round_id` column added to `scorecards`, `groups`, and `honours`. **`round_id` null means "this event's one-and-only round"** — an event with zero rows in `rounds` behaves exactly as before this feature existed, completely unaffected; this is deliberately fully backward-compatible rather than requiring every event to be migrated.

- **Admin UI**: a "Rounds" section on the event edit form (`roundsEditorHtml()`/`addRound()`/`saveRound()`/`deleteRound()`) — add/edit/remove rounds inline, each with its own label/date/course/tee-time/holes. An event with no rounds added there is a normal single-round fixture; the separate "Holes" dropdown on the main event form only applies when there are no rounds.
- **Live Scores** gains a round-selector (only shown for events that have rounds) alongside the existing event-selector, plus a special **"🏆 Overall (combined)"** option (`liveRoundId === null` on a multi-round event, vs. the same `null` meaning "the plain single round" when the event has no rounds at all — disambiguated everywhere by checking `roundsForEvent(eventId).length` first). Selecting a specific round scopes scoring entry, groupings, and the leaderboard to just that round (`scorecardFor()`, `getLeaderboard(eventId, holes, roundId)`, `matchGroups` filtered by `round_id`) — groupings are deliberately **not** shared between rounds (fresh groups each round, matching how a real society weekend runs; picking a round in the randomiser scopes `randomizerRoundId` via `openRandomizer()`/`ungroupedPlayersForEvent()` so Round 2 setup doesn't see Round 1's players as "already assigned"). Selecting "Overall" shows `combinedLeaderboard()` — total Stableford points per player summed across every one of their scorecards for the event, regardless of round — with its own "Finalise event" button (`finaliseEventOverall()`), enabled only once every round is finished.
- **Honours**: only the combined/overall finalise (`finaliseEventOverall()`) is actually reachable in the UI for a multi-round event — `renderLeaderboardView()` deliberately hides the per-round Finalise button once an event has rounds, so a multi-round event ends up with exactly one Hall of Fame entry, not one per round plus a combined one (tried both ways 2026-09-05 — showing all of them was confusing, since "the" result then depended on which tab happened to be open when Finalise was clicked). `finaliseScores(eventId, roundId)` still exists and still works (used by every normal single-round event, and still callable for an individual round if ever needed), it's just not exposed for a multi-round event's own rounds. The combined honour's title uses the **event's own name** in place of a course (`"{trophy} — {event.name}{noteSuffix}"`, e.g. `"Tour — Sheffield Tour (combined score over 2 rounds)"`) rather than trying to list every course the tour was played across — cleaner, and works for any tour name. `honours.winner_score` (added alongside this) stores the winning total captured at finalise time, shown in the Hall of Fame UI as a tap-to-reveal (`toggleHonourScore()`/`expandedHonourScoreIds`) next to the winner's name — null for historical/manually-added entries that predate this column, which just show no score.
- **Old unique constraint gotcha**: `scorecards` originally had `unique(event_id, player_id)` — wrong once a player needs one scorecard per round of the same event. Replaced with two **partial** unique indexes (`where round_id is not null` / `where round_id is null`) rather than a plain `unique(event_id, round_id, player_id)`, because Postgres treats `NULL` as distinct from `NULL` in an ordinary unique constraint — without the partial-index split, a single-round event's own duplicate-prevention (the offline queue's `23505` conflict handling in `processScorecardQueue()`) would silently stop working.
- **Leaderboard freshness**: realtime (`subscribeToLiveScores()`) is the primary update path and is normally near-instant, but a phone's websocket can silently drop (screen lock, network switch) with nothing to reconnect it. Two backstops added: a 20s background poll while the Leaderboard tab is actually open (`manageLeaderboardPoll()`, started/stopped from `renderLiveScores()`), and a manual "🔄 Refresh" button (`refreshLeaderboardNow()`) next to the live badge.
- **The standalone Groupings page** (`sec-groupings`/`renderGroupings()`/`addGroup()`) predates rounds and was **not** made round-aware (it's already the dead, unlinked entry point documented below) — if a multi-round event's groups are ever viewed there, every round's groups show intermixed. Not a real-world issue since nothing links to that page, but worth knowing if it's ever resurrected.

**Groupings** has two entry points that are easy to mix up: the standalone Groupings page (`sec-groupings`/`renderGroupings()`) is **not reachable from any nav link** (dead page, kept around but not linked) — the one people actually use is Live Scores → Groupings (`renderGroupingsInScores()`), a separate render function. Both share `matchGroups`/`matchGroupPlayers` state and the same underlying `groups`/`group_players` tables, but have their own `addGroup()`/`addGroupFromScores()` etc. — a fix applied to one doesn't automatically apply to the other, which has bitten before (see the `society_id` bug class above). The player picker in both now excludes anyone already assigned to another group for that event (only the group currently being edited keeps its own players visible/selected) — makes manual grouping usable with a full ~100-player roster.

A **"🎲 Randomise groups" button** exists on both entry points (`openRandomizer()`/`randomizerModalHtml()`, shared between both render functions): pick an event, get an auto-suggested 3s/4s group-size split for whoever's signed up and ungrouped (`computeGroupSizes()` — fewest groups, biggest first; totals under 6 or exactly 5 can't split cleanly into 3s/4s and are left as one group for the admin to adjust by hand), nudge individual group sizes or add/remove a group, then shuffle (`runRandomizer()`, Fisher–Yates) with a ~2.6s dice/shuffling-chip animation before the new groups fade in. Tee times continue from the last existing group (8 min apart) or the event's own tee time if none yet.

### GPS distances + proper scoring (2026-09-13)

The VPAR-inspired GPS/rangefinder + real stroke scoring feature (plan: shared course data → strokes/net Stableford → GPS distances → shared handicaps). Two new **shared, non-tenant-scoped** tables — `gps_courses` (id, name, postcode) and `course_holes` (gps_course_id, hole_number, par, stroke_index, green_lat/lng, green_polygon jsonb, tee_lat/lng, source) — deliberately have no `society_id`, unlike every other table in this app: a physical course's layout doesn't belong to one society, so two societies playing the same course (e.g. Studley Wood) share one imported copy. Each society's own `courses` row gets a nullable `gps_course_id` linking to it. RLS: public SELECT on both, writes via `is_admin()` called with **no argument** (checks "admin of *any* society" — the existing function already supported this without any change).

- **Courses is now its own top-level nav page (2026-09-13, same day)** — pulled out of a small sidebar widget on Events ("Course Ratings") into `sec-courses`/`renderCoursesPanel()`, reachable from the desktop tabs and the More drawer like Committee/Players/etc. A real card grid (`.course-card-grid`) — each card has a club-tie-striped banner (the same diagonal ink/claret/brass motif used elsewhere, standing in for photography this app doesn't have), a par/hole-count badge, postcode, star rating (unchanged rating flow), and a **Scorecard** toggle (`scorecardSummaryHtml()`) showing real par/yardage/stroke-index per hole once one exists, all visible to every visitor, not just admins.
- **Admin: "Manage course data"** — a button per card (`toggleGpsSetup()`/`gpsSetupPanelHtml()`), split into two clearly separate editors sharing the same shared/cross-society `gps_courses`+`course_holes` tables: **Scorecard** (`scorecardEditorHtml()`/`saveScorecardHole()` — par, yardage, stroke index; what players see and what net-Stableford scoring needs) and **GPS pins** (`gpsPinsEditorHtml()`/`saveGpsPin()` — green lat/lng only, used purely for the live distance readout while scoring). Both funnel through `courseHoleBasePayload()`/`upsertCourseHole()` so saving one never clobbers the other's columns on the same hole row. Getting there (once linked to a shared course): search+link an existing `gps_courses` row by name (`linkGpsCourse()`), import from OpenStreetMap (`importGpsCourseFromOsm()` — geocodes the course's postcode via the existing `geocodePostcode()`, queries the free public Overpass API for `golf=hole` ways (`ref`/`par` tags), `golf=green` ways (full boundary polygon — confirmed live that OSM maps real green shapes, not just a pin), and `golf=pin` nodes, spatially matching each green/pin to its nearest hole way), or add manually.
- **GPS lookup runs automatically now, not just on request** — `autoSetupGpsForCourse()` fires the moment a course gets a postcode with no `gps_course_id` yet (wired into `saveCourse()`, `saveNewCourseLibrary()`, `saveNewCourseFromEvent()` — every path that can set a course's postcode): checks for an existing shared match by name first, otherwise imports fresh from OpenStreetMap, entirely without an admin needing to open "Manage course data" at all. `courseGpsStatusBadgeHtml()` shows the live outcome right on the card — "⏳ Checking…"/"⏳ Importing…" while in flight, "📍 GPS distances available (N/18 holes)" once real pins exist, or "⚠️ No GPS data found automatically" if OSM has nothing for that course (pointing at the manual editor as the fallback). "Manage course data" always stays available for a from-scratch add, a correction, or a course with a name that doesn't match how another society already has it filed.
- **Deliberately kept open to any society admin, not platform-admin-only** — discussed explicitly: the shared `gps_courses`/`course_holes` tables are the one place in this app where a society's own admin can write data that affects every other society, breaking the "admin scoped to my own tenant" pattern used everywhere else. Decided to leave it as-is for now (crowdsourced, OSM-style — any admin can add or fix a course, which matters while the shared registry is still small) rather than gate it behind `is_platform_admin()`, since with effectively one real platform admin today that would just be friction with no real protection benefit — flagged as a one-line RLS change (`is_admin()` → `is_platform_admin()` on both tables' write policies) to revisit once there are genuinely multiple untrusted societies.
- **Strokes + net Stableford**: `hole_scores` gained a nullable `strokes` column; `events` gained `scoring_format` (`'stableford'` default/unchanged, `'strokes'`, `'match_play'` — a dropdown next to the existing free-text "Format" field on the event edit form). `netStablefordPoints()`/`holeAllowance()` (index.html, near the GPS helpers) compute net Stableford points from gross strokes + that hole's `par`/`stroke_index` + the player's `handicap`, using the standard stroke-index allocation — the computed points are what's actually written to `hole_scores.points`, so every existing leaderboard/finalise/honours code path needed **zero changes** for Stroke Play: summing points descending is mathematically identical to ranking by lowest net strokes ascending when every player played the same holes (the per-hole `2 + par − net` transform is linear, so total points = `2n + totalPar − totalNetStrokes`, a fixed offset per round). **Match Play is schema/dropdown-only so far** — selectable as a format but has no actual head-to-head pairing/leaderboard logic yet, deliberately deferred (needs a pairing concept in groupings this pass didn't build).
- **Focus Mode entry screen** (`renderFocusEntry()`) gained, both opt-in and never a blocker to scoring: a **GPS distance card** (front/center/back yardage, `gpsDistancesFor()` — center is a plain haversine to `green_lat`/`green_lng`; front/back project every `green_polygon` vertex onto the player→green sightline via a flat-earth approximation and take the nearest/farthest as front/back, collapsing to center when there's no polygon) driven by `navigator.geolocation.watchPosition()`, started/stopped by `manageFocusGpsWatch()` exactly when the entry view is showing (mirrors `manageLeaderboardPoll()`'s pattern) — patches only its own DOM slot (`renderGpsCardOnly()`) on each position tick so it never interrupts mid-tap on the strokes stepper; and a **strokes/quick-points toggle** (`toggleEntryScoreMode()`) shown only when the format is Stroke Play/Match Play *and* the current hole has both par and stroke index — the strokes stepper (`setStrokeScore()`) writes real strokes and shows the live net-points preview, and always falls back to the existing plain point-tap buttons when a hole/player lacks the data needed for the net-points formula (e.g. no handicap set).
- **Pre-round handicap confirm** (`renderHandicapConfirm()`/`confirmHandicap()`/`saveHandicapConfirm()`) — shown once per (event, round, player) per browser session (`handicapConfirmedKeys`), for **every** scoring format including plain Stableford (doesn't feed that round's own scoring, but keeps the shared handicap current for whatever else does need it) — a quick "Confirm your handicap: X — [Confirm] [Edit]" sheet before Focus Mode's entry screen, computed in `startScoring()`. Since live scoring is deliberately no-login/self-service (see RLS section), this edit can't go through the existing self-service `players` UPDATE policy (`auth.email()` match, which anon has none of) — needed a **new public UPDATE policy on `players`**, safe only because the pre-existing `protect_player_sensitive_columns()` trigger already reverts every column except `email`/`handicap` for non-admins; extended that trigger to also protect the two new columns below.
- **One shared handicap, with per-society overrides**: `players` gained `user_id` (→ `auth.users.id` — the *already-existing* cross-society identity, since Supabase Auth is one shared account platform-wide; backfilled by matching email) and `handicap_source` (`'shared'` default or `'override'`, admin-only toggle on the player-edit form: "Handicap mode"). A new `handicaps` table (user_id, handicap, recorded_at, source) holds the one official value + its history; `handicap_history` (user_id, player_id nullable, society_id nullable, handicap, recorded_at, source) is the merged, viewable log — a null `player_id`/`society_id` row came from the shared timeline, a scoped row from one society's override. All three are maintained by **one DB trigger** (`sync_handicap_change()` on `players`, `after update of handicap`) rather than client code — a shared-mode row's change logs to `handicaps`+`handicap_history` and fans out to every sibling `players` row (same `user_id`, still `'shared'`) via a nested UPDATE; `pg_trigger_depth() > 1` guards that recursive UPDATE from re-logging/re-fanning. My Account's Profile tab (`loadMyAccountHandicapInfo()`, lazy-loaded on first view since it's a cross-society lookup by `user_id` — not part of `loadData()`) shows the merged history and, for a shared-mode player who's in more than one society, a note naming which other societies a save here will also update.
- **The reveal-suspense freeze is now trophy-only**: `renderLeaderboardView()`/`renderFocusLeaderboard()` used to freeze/seal for *every* non-admin viewer past `blackoutHoleFor()`, regardless of the event. Both now gate that on `ev.trophy` being set (`isTrophyEvent`) — a casual round with no trophy assigned stays fully live end-to-end, any format; a genuine trophy fixture behaves exactly as before. A player's own scorecard (`renderFocusEntry()`) was never gated by the freeze in the first place and still isn't — the freeze only ever hides the shared comparison view.
- **Files**: new tables/columns/trigger/RLS policies run directly against Supabase, same as every other schema change in this file — see the SQL run for `gps_courses`/`course_holes`/`handicaps`/`handicap_history`/`courses.gps_course_id`/`hole_scores.strokes`/`events.scoring_format`/`players.user_id`/`players.handicap_source`/`sync_handicap_change()`. **One follow-up SQL statement is still pending manual application** (blocked by the auto-mode classifier, same as some other direct RLS writes have been): extending `protect_player_sensitive_columns()` to guard `user_id`/`handicap_source`, and adding the public UPDATE policy on `players` the pre-round confirm step needs — until that's run, the pre-round confirm step's "Edit" will fail to save for a non-admin (anonymous) scorer.

## iOS 26 status bar / toolbar colours (2026-09-23)

iOS 26 Safari and Home Screen web apps ignore `theme-color` (and the manifest's `theme_color`). The strip behind the clock takes the root `html`/`body` **background-color** — gradients (`background-image`) don't count, and unset means **white** — or the background-color of a fixed/sticky element at the top edge. The bottom toolbar takes a `position:fixed` element's background-color within 3px of the bottom edge (≥80% wide, ≥3px high), else the root colour. `apple-mobile-web-app-status-bar-style` was *not* the cause of the long-running white/black banner bug, despite a night of trying every value.

- `index.html`: its sticky maroon header tints the top; `html{background:#000}` is a safety net.
- `login.html`: `html{background-color}` = brand colour (CSS, `applyLoginPageBranding()`, and the edge function's first-paint style), the gradient starts on exactly that colour so there's no seam, and a mostly off-screen `.chin-tint` fixed black strip tints the bottom toolbar to match the page's black bottom.
- Any new full-screen page: set the root background-color to whatever colour the top of the page is. Only a real device can verify this; desktop previews can't show it.
